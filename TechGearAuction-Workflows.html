WF-01: Đăng ký tài khoản (Register)

📁 AuthController.cs → AuthService.RegisterAsync()

API Endpoint

MethodRouteAuthRequest Body
POST/api/auth/registerAnonymousRegisterDto { Email, DisplayName, Password }

Các bước xử lý (Steps)

  1. Kiểm tra email đã tồn tại → Nếu trùng: throw Exception("Email already exists")
  2. Kiểm tra Email ≤ 256 ký tự.
  3. Hash password bằng BCrypt.
  4. Tạo User entity với:
    • Role = User, Status = Active
    • AvailableCredits = 3 (Signup Bonus)
    • IsEmailVerified = false
    • EmailVerificationToken = GUID mới, hạn 24h
  5. Tạo CreditTransaction ghi nhận +3 credits "Signup Bonus".
  6. SaveChangesAsync()
  7. Gửi email xác thực qua IEmailService chứa link verify.

Điểm cần kiểm tra (Checklist)

  • ☐ Password validation (min length, complexity) chưa được kiểm tra ở backend.
  • ☐ DisplayName validation (max length, XSS) chưa có.
  • ☐ Link verify email hard-code http://localhost:8888 → Cần dùng config.
  • ☐ Nếu SendEmailAsync fail, user vẫn được tạo nhưng không nhận email → nên wrap trong transaction hoặc retry.
  • ☐ Không có rate-limiting cho endpoint register.

WF-02: Xác thực Email (Verify Email)

📁 AuthController.cs → AuthService.VerifyEmailAsync()

API Endpoint

MethodRouteAuthQuery Params
POST/api/auth/verify-emailAnonymousemail, token

Các bước xử lý

  1. Tìm User theo email. Không tìm thấy → return false.
  2. Nếu đã verify → return true (idempotent).
  3. So sánh token + kiểm tra expiry (24h).
  4. Set IsEmailVerified = true, xóa token.
  5. SaveChangesAsync()

Điểm cần kiểm tra

  • ☐ Endpoint dùng POST nhưng verify email thường là GET link (email client click).
  • ☐ Token không được hash → nếu DB bị leak, attacker có thể verify bất kỳ email nào.
  • ☐ Không có tính năng "Resend verification email".

WF-03: Đăng nhập (Login) + Anti-Spam Device Check

📁 AuthController.cs → AuthService.LoginAsync()

API Endpoint

MethodRouteAuthHeaders
POST/api/auth/loginAnonymousX-Forwarded-For, X-Device-Hash

Các bước xử lý

  1. Tìm User theo email.
  2. Kiểm tra Banned status:
    • Nếu user.Status == Banned → throw BannedUserException (kèm reason, violationCount).
  3. Kiểm tra Device Blacklist:
    • Tra BannedDevices theo X-Device-Hash → Nếu device bị ban → throw BannedUserException.
  4. Xác thực password qua BCrypt.Verify.
  5. Kiểm tra IsEmailVerified = true.
  6. Kiểm tra user.Status == Active.
  7. Lưu LastLoginIp và LastLoginDeviceHash.
  8. Tạo UserDeviceLog (IP, DeviceHash).
  9. Generate JWT token qua IJwtProvider.
  10. Trả về AuthResponseDto { UserId, Email, DisplayName, Role, Token }.

Điểm cần kiểm tra

  • ☐ Thứ tự check: Banned user check trước credential check → tiết lộ email có tồn tại hay không (thông tin bị lộ).
  • ☐ Không có cơ chế lock account sau N lần login thất bại.
  • ☐ JWT không có refresh token → user phải login lại khi token hết hạn.
  • ☐ Không có logout / token revocation.

WF-04: Quên mật khẩu & Đặt lại mật khẩu

📁 AuthController.cs → AuthService.ForgotPasswordAsync() / ResetPasswordAsync()

API Endpoints

MethodRouteAuthBody / Query
POST/api/auth/forgot-passwordAnonymousForgotPasswordDto { Email }
POST/api/auth/reset-passwordAnonymousResetPasswordDto { Token, NewPassword }

Các bước xử lý – Forgot Password

  1. Tìm user theo email. Nếu không tìm thấy → silent return (không quăng lỗi – tránh dò email).
  2. Tạo PasswordResetToken (GUID), expiry = 15 phút.
  3. SaveChangesAsync()
  4. Gửi email chứa token/link reset.

Các bước xử lý – Reset Password

  1. Tìm user theo PasswordResetToken.
  2. Kiểm tra expiry.
  3. Hash mật khẩu mới bằng BCrypt.
  4. Xóa token reset.
  5. SaveChangesAsync()

Điểm cần kiểm tra

  • ☐ Reset link hard-code http://localhost:8888.
  • ☐ Password reset token không hash → DB leak sẽ bị compromise.
  • ☐ Không có rate-limiting cho forgot-password (abuse gửi nhiều email).
  • ☐ NewPassword validation chưa có ở backend.

WF-05: Vòng đời Phiên đấu giá (Auction Lifecycle)

📁 AuctionsController.cs → Commands: Create, UpdateDraft, UploadImage, Publish, Cancel

Trạng thái Auction

Draft Scheduled Active Completed Cancelled

State Machine

Draft → (Publish) → Scheduled hoặc Active → (EndTime hoặc BuyNow) → Completed

Draft / Scheduled → (Cancel) → Cancelled

Active / Scheduled / Draft → (Admin Force Cancel) → Cancelled

API Endpoints

MethodRouteAuthMô tả
POST/api/auctionsAuthorizedTạo auction mới (Draft)
PUT/api/auctions/{id}AuthorizedCập nhật Draft
POST/api/auctions/{id}/imagesAuthorizedUpload hình ảnh (max 10, max 5MB, JPG/PNG/WebP)
PUT/api/auctions/{id}/publishAuthorizedPublish: Draft → Scheduled/Active, trừ 1 credit
PUT/api/auctions/{id}/cancelAuthorizedHủy: Draft/Scheduled → Cancelled (hoàn credit nếu Scheduled)
GET/api/auctionsAnonymousDanh sách auction (search, filter, paging)
GET/api/auctions/{id}AnonymousChi tiết auction
GET/api/auctions/trendingAnonymousAuction trending
GET/api/auctions/ending-soonAnonymousAuction sắp kết thúc
GET/api/auctions/recent-winnersAnonymousNgười thắng gần đây
GET/api/auctions/feedAuthorizedFeed từ người đang follow
GET/api/auctions/meAuthorizedAuction của tôi

Bước 1: Tạo Auction (CreateAuctionCommand)

  1. Validate: StartPrice ≥ 0, BidIncrement > 0, BuyNowPrice ≥ StartPrice, EndTime > StartTime, Title ≤ 200 chars, Duration ≥ 3h.
  2. Kiểm tra Category tồn tại.
  3. Tạo Auction với Status = Draft, CurrentPrice = StartPrice.
  4. Convert StartTime/EndTime sang UTC.
  5. SaveChangesAsync()

Bước 2: Upload hình ảnh (UploadAuctionImageCommand)

  1. Kiểm tra auction tồn tại + thuộc về seller hiện tại.
  2. Chỉ upload được khi Status = Draft hoặc Scheduled.
  3. Max 10 ảnh / auction.
  4. Upload lên MinIO bucket "auctions" qua IStorageService.
  5. Ảnh đầu tiên tự động set IsPrimary = true.

Bước 3: Publish (PublishAuctionCommand)

  1. Kiểm tra chủ auction + Status = Draft.
  2. Phải có ≥ 1 ảnh.
  3. Seller phải có ≥ 1 credit.
  4. Trừ 1 credit + tạo CreditTransaction (-1).
  5. Tăng TotalAuctionsCreated trên User.
  6. Nếu StartTime ≤ now → Status = Active; ngược lại → Scheduled.

Bước 4: Cancel (CancelAuctionCommand)

  1. Kiểm tra chủ auction.
  2. Active auctions KHÔNG thể cancel (có thể đang có bidders).
  3. Chỉ Draft / Scheduled mới cancel được.
  4. Nếu Scheduled → hoàn 1 credit + tạo CreditTransaction (+1 "Refund").

Điểm cần kiểm tra

  • ☐ Không có logic chuyển Scheduled → Active khi StartTime tới (chỉ background service xử lý EndTime, không xử lý StartTime).
  • ☐ Không thể delete ảnh đã upload.
  • ☐ Publish validation chỉ kiểm tra Status = Draft, không kiểm tra Scheduled (nếu muốn re-publish).
  • ☐ File upload ở controller validate extension nhưng command không re-validate → inconsistency nếu gọi command trực tiếp.

WF-06: Đặt giá thầu (Place Bid) + Anti-Shill Detection

📁 AuctionsController.cs → PlaceBidCommand

API Endpoint

MethodRouteAuthHeaders
POST/api/auctions/{id}/bidsAuthorizedX-Forwarded-For, X-Device-Hash

Các bước xử lý

  1. Kiểm tra Auction tồn tại + Status = Active + EndTime chưa qua.
  2. Seller không được bid trên auction của mình.
  3. Block Check: Kiểm tra UserBlocks giữa bidder ↔ seller (cả 2 chiều).
  4. Tính minimumBid = CurrentPrice + BidIncrement. BidAmount phải ≥ minimumBid.
  5. BidAmount không được ≥ BuyNowPrice (nếu có) → hướng dẫn dùng Buy Now.
  6. Tạo Bid entity (kèm IpAddress, DeviceHash).
  7. Anti-Shill Detection (Module 5):
    • Check 1: So sánh IP/DeviceHash của bidder với LastLoginIp/LastLoginDeviceHash của seller → Nếu match: tạo SuspiciousActivity, tăng SuspiciousSellerCount & SuspiciousBidderCount.
    • Check 2: So sánh với IP/DeviceHash của các bidder khác trên cùng auction → Nếu match: tạo SuspiciousActivity.
  8. Cập nhật auction.CurrentPrice = BidAmount.
  9. SaveChangesAsync() với Optimistic Concurrency Control (RowVersion) → Nếu conflict: throw ConcurrencyException.
  10. Gửi SignalR notification: NotifyNewBidAsync + NotifyPriceUpdateAsync.

Điểm cần kiểm tra

  • ☐ Anti-shill chỉ GHI LOG, không CHẶN bid → attacker vẫn thao túng được giá cho đến khi admin review.
  • ☐ Không có giới hạn số lần bid liên tục (spam bid).
  • ☐ Không kiểm tra bidder có bị Banned hay không trước khi cho bid.
  • ☐ BuyNowPrice check dùng >= → bid bằng đúng BuyNowPrice - BidIncrement vẫn hợp lệ nhưng không trigger buy now.

WF-07: Mua ngay (Buy Now)

📁 AuctionsController.cs → BuyNowCommand

API Endpoint

MethodRouteAuth
POST/api/auctions/{id}/buy-nowAuthorized

Các bước xử lý

  1. Validate: Auction tồn tại, Active, chưa hết hạn, có BuyNowPrice.
  2. Seller không được mua auction của mình.
  3. Block Check giữa buyer ↔ seller.
  4. Tạo Bid với giá = BuyNowPrice.
  5. Set auction.Status = Completed, auction.WinnerId = bidderId.
  6. Tạo ChatRoom (Active, expires 30 ngày) + SystemMessage "Phòng chat tự động khởi tạo".
  7. SaveChangesAsync() với OCC.
  8. Gửi NotifyAuctionEndedAsync qua SignalR.

Điểm cần kiểm tra

  • ☐ Không chạy Anti-Shill detection cho Buy Now (khác với Place Bid).
  • ☐ Không kiểm tra buyer có bị Banned không.
  • ☐ Các bid trước đó của người khác bị mất quyền lợi mà không được notify riêng.

Block User – Workflow đặc biệt

  1. Không được tự block mình.
  2. Tạo UserBlock record.
  3. Tự động xóa Follow 2 chiều giữa blocker ↔ blocked.
  4. Rollback giá Auction: Duyệt tất cả Active auctions của blocker → Nếu blocked user đang là Top Bidder:
    • Cancel TẤT CẢ bids của blocked user trên auction đó (IsCanceled = true).
    • Tính lại CurrentPrice = highest valid bid còn lại, hoặc StartPrice nếu không còn bid.
    • Gửi NotifyPriceUpdateAsync qua SignalR.

Điểm cần kiểm tra

  • ☐ Block chỉ rollback auctions của BLOCKER, không rollback auctions của BLOCKED → nếu blocker đang bid trên auction của blocked, bid đó vẫn tồn tại.
  • ☐ Watch: Seller không được watch auction của mình (đã validate), nhưng không kiểm tra user bị block bởi seller.
  • ☐ Unblock không khôi phục lại bids đã cancel → mất vĩnh viễn.

ChatRoom tạo tự động khi

Send Message Flow

  1. Kiểm tra ChatRoom tồn tại + không Archived.
  2. Chỉ seller hoặc winner mới được gửi tin.
  3. Block Check: Nếu 1 trong 2 bên block → không gửi được.
  4. Parse MessageType (Text, Image, Video, SystemText).
  5. Auto-unarchive: Nếu seller gửi → bỏ archive phía winner; ngược lại.
  6. Lưu ChatMessage, IsRead = false.
  7. Gửi realtime qua IChatNotificationService.NotifyNewMessageAsync (SignalR).

Điểm cần kiểm tra

  • ☐ Upload media không có file size limit ở command (chỉ có ở controller cho auction images, không có cho chat media).
  • ☐ Không có rate-limiting cho send message (spam).
  • ☐ MarkAsRead gửi SignalR notification cho TỪNG message → nhiều message = nhiều call SignalR → nên batch.
  • ☐ ChatRoom chỉ dành cho 1:1 (seller ↔ winner), không hỗ trợ group.

Create Report Flow

  1. Không được tự report mình.
  2. Kiểm tra reported user, auction (nếu có), chat room (nếu có) đều tồn tại.
  3. Tạo Report với Status = Pending.

Resolve Report Flow (Admin)

  1. Admin chọn 1 trong 3 hành động:
    • Reject: Status → Rejected. Không ảnh hưởng user.
    • IssueStrike: Status → Resolved. ViolationCount++. Nếu ≥ 5 → AUTO-BAN + blacklist device.
    • DirectBan: Status → Resolved. Ban user ngay + blacklist device.
  2. Tạo AdminAuditLog.
⚠️ Cảnh báo: Khi Auto-ban (5 strikes), ban logic thực hiện trong method riêng nhưng không tạo AdminAuditLog riêng cho hành động ban → khó truy vết.

Điểm cần kiểm tra

  • ☐ Không có trạng thái "Investigating" trong flow (enum có nhưng không dùng).
  • ☐ User có thể report cùng 1 người nhiều lần → spam report.
  • ☐ Không notify user bị report hoặc user report khi có kết quả.
  • ☐ ReportStatus enum có Dismissed nhưng chưa có flow sử dụng.

WF-12: Kháng cáo Banned (Appeal)

📁 AppealsController.cs → SubmitBanAppeal, ResolveAppeal

API Endpoints

MethodRouteAuthMô tả
POST/api/appeals/banned-usersAnonymous (banned user gửi)Gửi kháng cáo kèm bằng chứng
GET/api/appealsAdminDanh sách appeals
PUT/api/appeals/{id}/resolveAdminDuyệt / Từ chối appeal

Submit Ban Appeal Flow

  1. Tìm user bằng email (Anonymous endpoint – user đã bị ban không login được).
  2. Kiểm tra user.Status == Banned (nếu không bị ban → throw).
  3. Upload evidence files lên MinIO (images → bucket "images", khác → "chat-media").
  4. Tạo Appeal với Status = Pending + các AppealEvidence.

Resolve Appeal Flow (Admin)

  1. Nếu Approve:
    • User.Status → Active.
    • Xóa device khỏi BannedDevices.
    • Nếu ViolationCount ≥ 5 → giảm xuống 4 (tránh auto-ban lại ngay).
  2. Nếu Reject: Appeal.Status → Rejected. User vẫn bị ban.
  3. Tạo AdminAuditLog.

Điểm cần kiểm tra

  • ☐ Banned user có thể gửi nhiều appeal cùng lúc (không giới hạn).
  • ☐ Evidence bucket routing: video file sẽ vào "chat-media" thay vì bucket riêng → lẫn với media chat.
  • ☐ Approve chỉ giảm ViolationCount xuống 4 → nếu nhận thêm 1 strike sẽ bị ban lại ngay.
  • ☐ Không notify user khi appeal được resolve.

WF-14: Background Services (Tự động)

📁 Infrastructure/Services/AuctionClosingBackgroundService.cs, ChatRoomArchivingBackgroundService.cs

Service 1: AuctionClosingBackgroundService

Tần suấtChức năng
Mỗi 10 giâyĐóng auction hết hạn
  1. Query tất cả Auctions: Status = Active AND EndTime ≤ now.
  2. Với mỗi auction:
    • Có bid: WinnerId = highest bidder, Status = Completed. Tạo ChatRoom (30 ngày) + SystemMessage. Gửi SignalR notification.
    • Không có bid: Status = Completed (dù không có winner).
  3. Batch SaveChangesAsync() cho tất cả auctions.
🔴 Lỗi tiềm ẩn: Auction không có bid vẫn set Status = Completed thay vì Cancelled hoặc trạng thái riêng "Unsold" → gây nhầm lẫn khi query. Comment trong code ghi "Or Cancelled/Unsold" nhưng code thực tế set Completed.

Service 2: ChatRoomArchivingBackgroundService

Tần suấtChức năng
Mỗi 1 giờArchive chat room hết hạn
  1. Query ChatRooms: Status = Active AND ExpiresAt ≤ now.
  2. Set Status = Archived cho tất cả.

Điểm cần kiểm tra

  • ☐ Không có service chuyển Scheduled → Active khi StartTime tới → auction Scheduled vĩnh viễn không chuyển Active nếu Publish trước StartTime.
  • ☐ Auction closing query không lọc bids có IsCanceled = true → winner có thể là bidder đã bị cancel.
  • ☐ Background service batch save: Nếu 1 auction lỗi, toàn bộ batch rollback.
  • ☐ Polling 10s cho auction closing có thể gây tải DB nếu có nhiều auction.

Khi nào hệ thống gửi realtime?

  • PlaceBid: NotifyNewBidAsync + NotifyPriceUpdateAsync → AuctionHub
  • BuyNow: NotifyAuctionEndedAsync → AuctionHub
  • AuctionClosingService: NotifyAuctionEndedAsync → AuctionHub
  • BlockUser (cancel bid): NotifyPriceUpdateAsync → AuctionHub
  • ForceCancelAuction: NotifyAuctionEndedAsync → AuctionHub
  • SendMessage: NotifyNewMessageAsync → ChatHub
  • MarkAsRead: NotifyMessageReadAsync → ChatHub

Điểm cần kiểm tra

  • ☐ Notification entity (persisted) chỉ có endpoint đọc → không có logic tạo notification trong code command → chỉ dùng SignalR (volatile), không persist.
  • ☐ Nếu user offline, notification SignalR bị mất → cần message queue hoặc persistent notification.
  • ☐ AuctionHub và ChatHub rất mỏng (< 10 dòng) → logic realtime nằm trong service, hub chỉ expose.
